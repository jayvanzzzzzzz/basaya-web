# Lesson modules

## Learning paths

The staff Lessons workspace has Learning Paths, Modules and Lesson library tabs. Teachers and admins can create paths with a title, explicit Private/Shared visibility and 1–20 ordered modules (up to 200 unique lessons). New paths default to Private; existing visibility is preserved on edit. Teachers see their own and Shared paths, while admins can read/manage all paths for moderation. Only the creator edits a path. Shared paths must contain only Shared modules and lessons; privatizing a module referenced by a Shared path is blocked until the path is Private or the module is replaced. Archive/restore/delete reuse the audited lifecycle API; admin moderation of another creator's path requires a note and sends an owner notice. Assigned paths show an In use badge and omit Delete from their menu. Deletion is also permanently blocked on the server by everAssigned and assignment/progress checks, including legacy assignments without the flag. Changing path visibility preserves class assignment snapshots. Deleting an unused path never deletes modules or lessons. Referenced modules cannot be deleted.

Class assignment can select a path, customize lesson copies inside its module list, review order, and save module versions before assignment. Lesson copies save to the library immediately; cancelling assignment retains these copies. Module copies are cached for assignment retry. Assigning a path writes an immutable module/lesson snapshot and one opening date/deadline to all class lesson links transactionally. Duplicate lessons already assigned as that mode are rejected instead of silently receiving different deadlines. Existing individual/module assignment remains available. Changing a path lesson's schedule in the class updates the whole assigned path. Individual extensions are disabled for path members. Later library edits or archival never rewrite class content/progress.

Deploy the content-lifecycle API, lesson-deadlines handler, Firestore rules and web assets together. No existing records are migrated. Assigned classroom lesson paths now use the teacher-defined teaching sequence described below.

Checks: `node tools/learning-path-tests.mjs <java.exe> <emulator.jar>` tests the real backend and rules; `node tools/learning-path-browser.cjs` tests teacher/admin path creation UI and previews with local adapters, including desktop/mobile light/dark layouts. The browser suite also covers editing a lesson copy during module assignment, saving its module version, and preserving the originals; the real backend suite verifies learning-path assignment transactions.

Both staff portals use `js/lessonWorkspace.js` at `#/lessons`. The existing lesson studio mounts inside the workspace; its content sections and validation remain shared with the admin library.

## Stored structure

`modules/{id}` contains `title`, `description`, `ownerId`, `visibility`, `lessonIds`, `revision`, `createdAt`, `updatedAt`, `progression`, and `lockingEnabled`. The position of each ID in `lessonIds` is its authoritative learning order. Modules accept 1–100 unique lessons. Revision checks prevent overwriting another session's changes.

New modules and lessons default to Private. Authors can choose Shared to make content available to teachers and admins. Private modules and lessons are visible only to their author in staff libraries; assigned students retain lesson access. Admins do not have a private-library read exception. Teachers can reuse Shared modules. Content changes create a module owned by the editor; visibility-only changes require the owner or an admin.

Selecting a premade lesson reuses its ID. Every saved content edit creates a separate lesson or module; the selected record and its existing class assignments are preserved. Keeping the title produces names such as Pandiwa - 1.1, Pandiwa - 1.2; a changed title is saved exactly as entered, without a numeric suffix. Later edits using that new name start its own sequence. A saved version's editable title field shows its base title rather than stacking suffixes.

Only changing Library visibility updates the selected record in place; it never rewrites lesson sections or makes a copy. Saving an existing lesson or module without changing its title/content shows an Edit required to save a copy dialog on Save, keeps the editor and chosen visibility intact, and sends no save request. Visibility selection itself never opens a restriction dialog. Owners/admins can still save visibility-only updates in place; other teachers must edit content before saving their own copy. sourceLessonId/sourceModuleId track lineage, copiedFromLessonId/copiedFromModuleId identify the selected version, and versionBaseTitle/versionNumber track the title sequence. New versions belong to the editor and never inherit adminManaged creator rights.

The authenticated content-lifecycle API reserves lesson drafts and saves module versions. Server-only contentVersionCounters serialize same-name allocations; contentVersionRequests make lost-response retries idempotent. Failed section batches reuse the reserved draft. If publication actually succeeded and the editor is changed after an acknowledgement failure, it reserves a new version rather than overwriting the published one. Renaming an unfinished failed attempt receives a new reservation. Dictionary-audio sync warnings do not turn a published version into an apparent failed save.

New lessons and copies are first reserved with `publicationState: draft`. A single batch publishes their activity sections and marks the root `published`. The staff libraries omit unfinished drafts. A retry reuses the reserved lesson ID and number. Existing lesson IDs, class assignments and student progress are preserved.

The teacher classroom **Add modules** page assigns lessons through modules only; individual lesson selection is unavailable. The page retains the module queue, saved lesson order, assessment/practice choices, schedule controls, and final sequence preview. If no modules are available, **Go to modules** opens the Lessons workspace. Existing class assignments and saved scores are preserved. New links retain `moduleId`, `moduleTitle`, `moduleOrder`, and `moduleRevision`, along with the existing class order. Already assigned lessons are skipped according to the selected mode. Assignments are snapshots; editing a module does not silently replace an existing class's assignments.

## Module creation and assignment previews

In **Learning order**, each lesson has a **Move to** position dropdown. Choosing a position shifts the other lessons and renumbers the list immediately; it does not save until the module is submitted. The moved row is briefly highlighted and retains keyboard focus. **Undo** reverses the latest move within that module draft. Adding, removing, or replacing a lesson clears an outdated Undo action. The count shows the number of lessons, and a single lesson's position control is disabled. The controls support the existing light/dark themes and reduced-motion preference. Run `node tools/module-lessons-browser.cjs --order-only` for focused browser coverage and the 16 teacher/admin desktop, tablet, and mobile layouts in `audit/lesson-order`.

The builder supports up to 20 module drafts through **Add another module**. Each draft retains its own details and lesson order. Teachers can switch drafts, move modules up/down, or remove a draft without deleting saved library lessons. Save opens an ordered preview with the lessons nested under each module. Cancelling writes nothing. Successful modules are removed from the pending queue, so a later failure preserves only the remaining drafts for retry. Modules remain independent library resources; their class sequence is chosen during assignment.

The class assignment picker queues modules, provides ordering controls, and previews the existing assignments followed by the proposed modules and their actual new lessons before committing. Existing lessons of the selected assessment/practice type are skipped and disclosed. Modules sharing a lesson within the same queue are rejected because each class lesson/type has a single link. New work uses the highest existing class order plus one rather than the link count, preserving append behavior after deletions. Up to 200 lessons can be assigned in one module queue. Existing assigned work is not rearranged by these controls.

`node tools/module-lessons-browser.cjs` also checks multi-module draft ordering, nested previews, cancel without writes, partial-save retry without duplicates, append after a sparse existing order and after previously assigned modules, and responsive light/dark previews. These changes do not activate student locking or change practice completion tracking.

## Assigned lesson path progression

The classroom picker supports multiple paths and Move up/Move down controls before assignment. Selection order is the teaching sequence; alphabetical order is only used in the library picker. New paths append after existing assignments. Classroom path rows and student lesson cards follow the saved sequence. Module and lesson order within each path is preserved.

Teacher classrooms and student home show assigned lesson paths only. Individual assignments remain stored for progress and scoring but are not duplicated in these main lists. A student opens an unlocked path to see its lessons and download controls, with a back button to return to the path list. The teacher's hamburger menu on each path contains Extend deadline, Edit schedule and Archive lesson path; Notify students appears when delivery is pending. Extension uses a dedicated form and saves the deadline for the entire path. Edit schedule retains the neighboring-path opening-date checks. Archived paths keep a Restore action. Run tools/class-path-list-browser.cjs and tools/learning-path-home-browser.cjs for these interfaces, keyboard/menu behavior and light/dark mobile layouts.

Students must finish all required lessons in earlier active Assessment paths before opening a later path. Completion uses existing finished flags, excluding skipped parts. Pending pronunciation review is unfinished. The next path must also have reached its opening time; existing deadline/review rules still apply. Practice paths do not become prerequisites because practice records no results. Exempt lessons and work closed before enrollment do not trap students behind inaccessible prerequisites. Archiving removes a path from progression without deleting progress; restoration returns it to its sequence position and checks its opening date against its neighbors.

Opening dates must be on strictly later calendar days than the preceding assigned path in Asia/Manila time. If the first path opens immediately, its assignment time supplies the effective date. Calendar bounds and typed-date validation enforce this in the teacher form. Editing an assigned schedule checks both neighbors. The API repeats these checks inside serialized Firestore transactions, including concurrent appends. New assignments store order and sequenceOpenAt; links also store learningPathOrder. Legacy order comes from class lesson links without migrating records.

The shared policy is js/learningPathSequence.js; run node tools/build-learning-path-sequence.mjs after editing it to regenerate notify-api/lib/learningPathSequence.js. Web cards, direct lesson/part URLs, downloads, and assessment/fluency requests enforce progression. Downloads retain prerequisite identities and use cached confirmed progress; missing prerequisite progress stays locked. Module lockingEnabled fields are unchanged. Android UI is outside this web change; its assessment requests receive the same API protection.

Run node tools/learning-path-sequence-tests.mjs with Java and the emulator jar for API/rules, dates, completion, skipped/review parts, concurrency, retry, archive/restore and offline policy. Browser checks: tools/class-path-batch-browser.cjs, tools/learning-path-lock-browser.cjs and tools/learning-path-home-browser.cjs. Release the API, generated policy, rules and web assets together.

## Archive workflow

Inside a teacher's classroom, assigned lessons and whole lesson paths use Archive instead of Remove. The class's Archived lesson paths section lists only archived path assignments; individually archived lessons do not appear there. The server moves assignment links into the class's private archivedClassLessons collection and preserves student progress and library content. Restoring a path restores all its saved links, including children individually archived earlier, and refuses to overwrite an existing assignment. The main Lessons library retains its original archive and delete controls.

Classroom Add Lesson Path opens a path-only assignment picker. A saved, active path is required even when standalone modules exist. Teachers review the full path, optionally customize lesson copies, and assign it through the learning-path API with one schedule and deadline; this screen no longer assigns standalone modules.

Both portals keep Modules and Lesson library on the same Lessons page. Each view has All (active accessible content), Created by me (active content owned by the signed-in account), and Archived ribbons. Teachers see their own archives; admins can also manage archives of Shared content. Private content remains owner-only. Older lessons without teacherId stay in All and are not falsely attributed in Created by me.

Archive and Restore use POST /api/content-lifecycle, routed through the existing consolidated function. Archive metadata is server-owned, with a transactionally written audit event and owner notice for moderation. Actions on content whose creator matches the signed-in account use a confirmation only. Admin moderation of content with a different recorded owner requires a reason, displayed to the owner on the Lessons page. Ownerless legacy Shared content is admin-managed and also uses confirmation only; ownership is never guessed or silently reassigned. A teacher cannot restore an admin-moderated archive. Restore retains visibility. Archiving a module never archives its lessons or edits existing class links/progress.

Archived content cannot be edited or assigned anew. Existing assigned students retain lesson/section access. The module builder and class assignment picker exclude archived content; database rules reject new links to archived lessons or modules. Archive/Restore and Delete permanently sit inside each item's hamburger menu. Direct root deletion is denied; only the authenticated content-lifecycle API can perform guarded deletion. The API checks current and legacy class links, module/copy references, active and historical student progress, and hashed assessment attempts. It fails closed if old progress cannot be mapped safely. Used content returns a conflict without being changed. For unused content, a server-owned deletionPending/archived barrier prevents new assignments and edits during recursive child cleanup; the root is deleted last with an audit record. A failed cleanup can be retried by the requesting account. Module deletion leaves reusable lessons intact. Stored audio objects are retained because URLs can be reused elsewhere.

No archival data migration is needed: missing archived means active. Release the API handler/route and Firestore rules with the web assets. The local implementation does not deploy them or archive production records. Tests: node tools/content-archive-tests.mjs <java.exe> <emulator.jar>, node tools/content-archive-browser.cjs, plus the existing module rules suite. Browser fixtures do not write production data.

## Library navigation

After an Archive, Restore, or Delete confirmation, the affected lesson/module displays an animated action icon and a live progress label beside its title. Its controls are disabled while the request is pending. Only a successful response triggers the completion check and a short exit transition before the library refreshes; failed requests leave the item available for retry. Reduced-motion mode keeps the progress text and static icon without animation. This feedback is shared by teacher module/lesson cards and admin lesson table rows.

The workspace owns a persistent header and Modules/Library plus collection ribbons. Library rendering is confined to data-workspace-body, and uses the already-loaded lesson snapshot. Switching tabs or All/Created by me/Archived performs no Firestore reads; entry and successful content mutations refresh the data. Initial lesson and module loads run concurrently. Difficulty filters update row visibility and pagination in place, retaining the search field, filter buttons and parent navigation.

Run node tools/library-navigation-browser.cjs to verify zero repeated reads, synchronous switches, stable header/navigation/list controls, combined search and difficulty filtering, rapid switching, empty and populated modules, keyboard focus, and desktop/mobile light/dark layouts. The archive and visibility browser suites also cover the shared page structure.

## Legacy lesson ownership recovery

The approved set of 26 existing lessons was made Shared and marked adminManaged in a one-time live update. This role-level flag gives admins creator controls and inclusion in their Created by me view, without inventing an individual creator UID. New lessons, copies and modules do not receive it. Teachers cannot grant this flag through client writes.

Before saving an existing legacy lesson as Private, the admin editor writes a canonical teacherId (preserving a recorded owner when present, otherwise the signed-in admin) and clears adminManaged. Rules reject Private roots with no canonical owner, preventing records from falling out of both the authored and Shared queries. Direct Edit lesson updates the original document; a separate copy exists only after Save copy succeeds. The save confirmation now makes that distinction explicit.

Run node tools/legacy-lesson-owner-browser.cjs for the reproducer and copy isolation check. The content archive emulator suite covers the protected admin flag and rejected ownerless Private saves. The live recovery report and pre-change metadata are in build/idyoma-audit; do not replay the migration for newly created lessons.
